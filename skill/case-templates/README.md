# case-templates —— 可套用的报告/验证/提交模板

> **类型**：案例模板
> **适用场景**：FPGA/PYNQ 竞赛作品、课程设计、项目验收
> **来源**：按赛方 3.3.5.1/3.3.5.3/3.3.5.4 的条目逐条拆出来的骨架，
> 再拿本项目实际踩过的口径问题磨了一遍（见第 5 节）。
> 顺序固定为：**先填验证矩阵，再填提交检查表，最后才有报告**。

---

## 1. 适用场景

- 比赛要交**设计报告 + 提交包**，但不知道评审会问什么；
- 项目做了很多验证，却说不清“每个功能点由哪一层证明”；
- 临提交发现漏文件、混进 `proj/`、脚本里还留着本机绝对路径。

## 2. 使用方法

| 模板 | 用途 |
|---|---|
| [`design_report_template.md`](design_report_template.md) | 设计报告骨架（对应赛方 3.3.5.3 各项） |
| [`verification_matrix_template.md`](verification_matrix_template.md) | 验证矩阵（仿真/台架/上板三层） |
| [`submission_checklist_template.md`](submission_checklist_template.md) | 提交前检查表（工程包/技能包/报告/目录/凭据） |

1. **先填验证矩阵**：它逼你把“怎么证明”想清楚，报告只是它的叙述版；
2. **再填提交检查表**：确保没有漏项、没有重物、没有绝对路径/凭据；
3. **最后写报告**：所有数字从矩阵/原始日志里抄，不凭记忆；
4. 负结果也写进报告：评委更看重“判断依据”，而不是“全是好消息”。

填空用的实例：本仓库 `report/` 就是用这三份模板产出的成品
（`design_report.md` / `llm_collaboration.md` + `figures/*.svg`）。

**注意**：目录/文件名用英文小写；中文只出现在正文；
数字必须带口径（单点/端到端、内核/含 AXI、逻辑/物理 lane）；每个结论给出证据路径。

## 3. 已验证的效果（本项目）

| 模板 | 结果 |
|---|---|
| 验证矩阵 | 覆盖 6 类对象（V3 束 / 粒子引擎 / PL 检测 / 画线 / 帧泵 / PC 台架），每行都能指到原始日志 |
| 提交检查表 | 3 类风险的检查项均已落地：缓存目录（`proj/`、`xsim.dir`）不得入包、可执行代码不得含本机绝对路径、部署包只允许当前 bit 的边车（这条是**实打实查出来的**：deploy 里曾有新旧两个 `.md5`，旧边车已移出，现在包里只剩一个） |
| 设计报告 | 产出 `report/design_report.md` + `.docx` + `.pdf`（A4 封面/页眉/章节分页），以及 `report/llm_collaboration.md` |
| 一致性 | 报告里每个数字都能回到原始文件：构建数据→`docs/reports/*.rpt`、`report/evidence/*.rpt`；上板/台架数据→`docs/reports/*.txt` 或项目交接记录 `HANDOFF.md` 的对应条目（后者是过程文档，未随提交包） |

> 注：两块 bit 的原始报告分两处放 —— `docs/reports/*.rpt` 对应 2026-10-31 的 8 粒基线
> `db96e197`；`report/evidence/*_2026-11-01.rpt` 对应 2026-11-01 的 16 粒交付 bit
> `67412907`。**引用时写清是哪一块 bit**，不要混。

## 4. 失效条件

| 条件 | 后果 | 替代做法 |
|---|---|---|
| 赛方模板更新 | 章节号/必填项对不上 | 每次开赛先读一遍官方 PDF，按它的条目重排 |
| 题目没有“上板”环节 | 三层验证矩阵只有两层 | 删掉上板行，把仿真层写细 |
| 数字口径未定义就填表 | 同一指标出现两个值 | 先在第 1 节写“数据口径说明”，再填表 |
| 报告先写、矩阵后补 | 数字无出处，返工 | 顺序固定：矩阵 → 检查表 → 报告 |
| 直接套用别人的措辞 | 与自己的实现不符 | 模板只给骨架，句子必须按本项目重写 |

## 5. 它是从哪些失败里总结出来的

1. **对外口径与实现脱节**：粒子数一度在外材料里写成 8 粒 / 32 粒两种说法，
   而 RTL 最后定的是 16 粒；2026-11-01 才统一（`HANDOFF.md`：
   “对外材料不再写 8/32 粒”）。⇒ 报告里的每个数字必须能指到矩阵的一行。
2. **旧 md5 边车残留**：`vivado/ov5640_pynq/deploy/` 里曾同时躺着
   `ov5640_m1a_wrapper.bit.md5`（新，`67412907`）与
   `ov5640_m1a_wrapper_949911fb.bit.md5`（旧，对应的 bit 早已不在包里）。文件名不带版本时，
   复制错了也不会报错 ⇒ 检查表加“部署包只允许当前 bit 的边车”；旧边车已移出
   部署包，现在 `deploy/` 里只剩 `ov5640_m1a_wrapper.bit.md5` 一个。
3. **证据里混进本机路径**：`docs/reports/cleanroom_build_2026-10-31.txt` 第 12 行
   留着 `D:/Desktop/PYNQ/_cleanroom2_20261031/...`。日志可以留（它是原始证据），
   但**可执行脚本里不许有** ⇒ 检查表把两者分开写（注释/日志可 WARN，代码 0 容忍）。
4. **报告与现役 bit 不同版本**：`docs/reports/README.md` 与 `report/README.md`
   一度把 `db96e197`（10-31 的 8 粒基线）写成“现役 bit”，而 deploy 里已是
   `67412907`（11-01 的 16 粒）。现已改为：两块 bit 并列列出、各自注明数据出处 ——
   16 粒那版的 Vivado 原始 `.rpt` 归档在 `report/evidence/`（文件名带 `_2026-11-01` 后缀）。
   ⇒ 检查表加“报告里每个 bit md5 都要与 deploy 对得上”，且**同一段里不许混用两块 bit 的数字**。
