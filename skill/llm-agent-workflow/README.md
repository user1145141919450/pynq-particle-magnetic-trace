# llm-agent-workflow —— 大模型协作提示词与智能体工作流

> **类型**：提示词工作流
> **适用场景**：用大模型（Claude/GPT/本地模型）辅助 FPGA/PYNQ 开发、且要求“可复现、可验证”的项目
> **来源**：本项目 18 个会话、多个 1M 上下文硬切、以及 8 类自我纠错案例。

---

## 1. 解决什么问题

大模型能显著加速 FPGA 开发，但有三个常见风险：

1. **输出与事实不一致**：说“改了/过了”，实际没改或没跑；
2. **静默回归**：构建 exit=0，但 bit 里是旧逻辑、BD 丢了 IP；
3. **口径漂移**：把单点指标说成端到端指标，把计划说成已完成。

本技能不是“更好的提示词大全”，而是**把模型放进一个有门禁的工程系统**：
让模型跑得快，让门禁说得准，让人做最终判断。

---

## 2. 四层约束模型

```
第 1 层：项目铁律（CLAUDE.md / RULES.md）
  ├─ 危险操作只允许一个入口（下 bit、烧卡、删库）
  ├─ 改 RTL 先过时序门禁
  ├─ 物理动作先问现场的人
  └─ 凭据零容忍
第 2 层：状态文档（HANDOFF.md）
  ├─ 当前 bit / 构建 / 上板状态
  ├─ 待办与优先级
  └─ 事故证据链
第 3 层：跨会话记忆
  ├─ 会话对照表
  ├─ 根因/口径/待办
  └─ 用户偏好与硬性要求
第 4 层：自动门禁
  ├─ 时序门禁、IP 基线、台架、逐位对拍、md5 对账
  └─ 提交前自检（文件/路径/凭据）
```

**关键**：第 1~3 层是“给模型看的约束”，第 4 层是“不依赖模型的验证”。
只有第 1~3 层，模型仍可能骗你；只有第 4 层，模型不知道为什么。

---

## 3. 使用方法（会话生命周期）

照着这条流水线走，就是在用这套工作流；每一步的产出都必须落盘，否则上下文一断就没了。

```text
接手指令
  → 读铁律 / 状态文档 / 记忆 / 指定会话
  → 用三句话复述：当前 bit、已完成、待办与风险
  → 选一个最小任务
  → 定位（日志/波形/源码/历史提交）
  → 改（RTL/PS/脚本）
  → 仿真 / 黄金模型
  → 构建 / 门禁
  → 上板 / 台架
  → 文档 / 提交 / 记忆
  → 下一个任务
```

**纪律**：每完成一块就 `git commit` + 更新状态文档 + 写记忆；
会话可能在任何时刻被上下文上限硬切，未落盘的工作等于没做。

## 4. 提示词工作流（摘要）

完整可复制模板见 [`prompts.md`](prompts.md)。六个核心模板：

| 场景 | 提示词要点 | 目的 |
|---|---|---|
| 接手 | “先读铁律/状态/对话 N，复述再动手” | 恢复上下文，避免重复踩坑 |
| 定位 | “先查现状，给证据链，不要凭记忆” | 把“猜”变成“查” |
| RTL 改动 | “改前门禁、改后清缓存/reset 所有 run/重跑逐位” | 防静默复用旧 dcp |
| 上板 | “先 probe，只用唯一入口，物理动作先问人” | 防挂总线/误动作 |
| 收尾 | “改了什么/验证了什么/还差什么；提交+落盘” | 防会话硬切丢工作 |
| 规格审计 | “规格与实现不一致就停下，给三个处理选项” | 对齐规格与口径 |

## 5. 智能体工作流设计

### 5.1 角色分工

| 角色 | 职责 | 不做什么 |
|---|---|---|
| 人类 | 定目标、拍板取舍、现场物理动作、最终验收 | 不逐行写重复代码 |
| 模型 | 定位、实现、跑仿真/构建、写文档、整理证据 | 不替人做物理动作/主观体验判断 |
| 门禁 | 时序、IP、台架、逐位、md5 | 不解释“为什么” |

### 5.2 并行工作线

- 构建、仿真、台架可以后台跑；
- **两个 Vivado 构建不能同时操作同一工程**；
- **两个 VDMA 客户端不能同时跑**；
- 文档线与构建线可以并行，但文档线不碰工程目录。

### 5.3 人类决策点（必须停下问）

- 物理动作（摆球/动相机/拍照/断电）；
- 规格口径（数字、叫法、对外表述）；
- 负结果是否接受（优化打平/失败后是否继续）；
- 时间/资源取舍；
- 提交内容与开源许可。

## 6. 失效条件

| 条件 | 后果 | 替代做法 |
|---|---|---|
| 没有版本控制 | 无法回滚/对比 | 先 `git init`，每块提交 |
| 没有测试/门禁 | 模型说“过了”不可信 | 先建最小台架/逐位对拍 |
| 让模型做物理动作 | 现场事故 | 人类操作，模型只给步骤 |
| 把凭据贴进对话 | 泄露 | 用占位符/环境变量；发现即停 |
| 无限制地长会话 | 1M 上限硬切 | 每块落盘 + 会话接力 |
| 只给模型“目标”不给约束 | 走捷径 | 铁律 + 验收标准 + 证据要求 |

## 7. 已验证效果（本项目）

- 18 个主会话（2026-09 → 2026-11-02），跨越多次上下文硬切仍能无损接手；
- 8 类自我纠错案例（见 `report/llm_collaboration.md` 第 3 节）：
  16 粒命名、幽灵写、HDMI 相位、SD 卡假成功、帧泵打平、检测资源攻坚、丢 IP、会话硬切；
- 产出：RTL/PS 代码、构建脚本、测试台、台架（PC 489 / 板 488）、技能包、设计报告；
- 关键数字：V3 17/17、PE 2000 子步逐位（16 粒 `tb_pe_axi` 13/13）、检测 9/9/8/8、
  画线 3523 像素、帧泵 0/921600。

## 8. 来源失败（为什么值得做）

1. **注释与译码不一致**：pe_axi 的 `.KLANES(4)` 注释与实际 `KLANES(1)` 不符，
   模型一度按注释汇报；后来规定“注释/文档必须与译码/RTL 对账”。
2. **构建 exit=0 但丢 IP**：从零重建后通过 `.hwh` 产物对账发现；
   此后固化 `finish_build.py` 和 `ip_baseline.json`。
3. **规格变更只改文案**：并行度调整没有同步 RTL/驱动/台架，后来搜全链路补齐，
   并把“规格变更要落到实现和验证链”写进提示词模板。
4. **1M 上下文硬切**：对话 3/4/5/6/7/8/10/11/12/13/17 都被硬切；
   此后规定“每完成一块就提交+落盘”。

## 9. 迁移到别的题目

1. 写一份 `RULES.md`（危险操作/门禁/物理动作/凭据）；
2. 写一份 `HANDOFF.md`（当前状态/待办/证据链）；
3. 建最小门禁：构建脚本 + 一个逐位对拍 + 一个提交前自检；
4. 用 `prompts.md` 的模板开始；
5. 每块结束提交 + 更新状态；
6. 定期用“规格审计”提示词核对对外口径。

这套方法对任何“硬件/嵌入式 + 可验证”的项目都适用，不限于 FPGA。
