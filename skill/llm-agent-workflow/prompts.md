# 提示词模板（可直接复制）

> 这些模板来自本项目 18 个会话的真实使用与迭代。使用方法：
> 把 `<...>` 替换成你的项目信息；不要一次让模型做太多，按“定位 → 改动 → 验证 → 收尾”分步。
> 所有模板都默认一个前提：**你有版本控制、能回滚、有最基本的测试/门禁**。
> 没有这些前提时，先补基础，再谈大模型加速。

---

## 1. 接手会话

```text
先读项目根目录的 RULES.md / CLAUDE.md 与 HANDOFF.md；
再查会话记录“<对话 N>”（目录：<路径>）。
用三句话复述：
1) 当前 bit/构建/上板状态；
2) 已完成的关键工作；
3) 待办与最高风险。
不要先动手，等我确认。
```

**期望输出**：状态复述 + 你指出其中过期/矛盾的地方。
**失效**：HANDOFF 没更新 → 复述会过期；所以每块必须落盘。

---

## 2. 定位问题（先查再改）

```text
现象：<一句话描述 + 复现步骤 + 期望/实际>。
先查现状：相关日志、寄存器/波形、源码、最近提交、历史事故记录。
给出：
- 证据链（每条指向文件/行/日志/波形）；
- 最可能的 2~3 个根因，按概率排序；
- 最小验证实验（不要一上来大改）。
不要凭记忆下结论。
```

**期望输出**：证据 + 排序 + 最小实验。
**失效**：没有可观测信号 → 先补探针（日志/ILA/计数器）。

---

## 3. 最小改动

```text
基于上面的定位，给出最小改动方案：
- 改哪些文件/函数/寄存器；
- 为什么这是最小改动；
- 会影响哪些既有功能；
- 怎么验证（单测/仿真/台架/上板）。
先不要改，等我看方案。
```

**期望输出**：改动清单 + 影响面 + 验证方法。
**失效**：影响面说不清 → 说明你还没定位到根因。

---

## 4. RTL 改动（防静默复用）

```text
改 RTL 前：
1) 跑 timing_gate.tcl 记录基线 WNS/WHS；
2) 确认当前 bit 与源码版本（md5/commit）。

改完后必须：
1) 用 build_after_patch.tcl（清 .cache/.gen、reset 所有 OOC 子运行）；
2) 重跑黄金模型/测试台，逐位对比；
3) 过时序门禁；
4) 给出改动前后对比表 + 证据路径。

不要用“综合通过”代替“逐位一致”。
```

**期望输出**：基线/改动后对比 + 门禁日志 + 逐位结果。
**失效**：只跑父级 reset → 旧 dcp 会静默复用。

---

## 5. 仿真/黄金模型

```text
为 <模块> 写一个确定性测试：
- 用 Python 定点模型生成期望值（与 RTL 同口径）；
- testbench 逐元素比较，失败时打印 index/expected/actual；
- 覆盖：正常路径、边界、越界、空输入、反压；
- 长跑至少 <N> 步（不要只跑短跑）。

给出：测试命令、期望输出、当前结果。
```

**期望输出**：可复现的测试 + 第一处差异定位。
**失效**：浮点/随机 → 改容差比较或固定种子。

---

## 6. 构建/门禁

```text
构建后按顺序检查，任何一步失败就停：
1) 时序门禁 WNS/WHS >= 0（违例 bit 是否改名 .TIMING_FAILED）；
2) .hwh 与 ip_baseline.json 逐 IP/地址对账（有没有丢 IP/复活 ILA）；
3) bit/hwh 是否进 deploy；
4) deploy_check 源↔部署 md5 是否一致；
5) 记录本次 bit md5 与构建 commit。

不要只看 Vivado 返回码。
```

**期望输出**：五项检查结果 + bit md5 + commit。
**失效**：没有基线文件 → 首次构建后生成。

---

## 7. 上板

```text
上板前按顺序：
1) pl_probe：PL 里现在是什么（rc=0/1/9）；
2) vdma_state：有没有野 DMA（RS=1 且没有你的客户端 → 先 halt）；
3) 只用 load_bit.py（唯一入口），校验 bit md5；
4) 下完再 probe 一次；
5) 跑对应台架，贴原始输出（不要只贴“通过”）。

任何一步不符合预期就停，不要“再试一次”。
物理动作（摆球/动相机/拍照/断电）先问我“准备好了没有”。
```

**期望输出**：每步原始输出 + 结论。
**失效**：`pl_probe` 返回 9（说不清）→ 不下 bit。

---

## 8. 规格审计 / 口径核对

```text
在写进报告/对外介绍之前，先核对：
- 规格数字（并行度、频率、帧率、倍数）是否与 RTL/实测一致；
- 测量口径（单点/端到端、内核/含 AXI、逻辑/物理 lane）是否写清；
- 有没有把“计划/部分完成”说成“已完成”。

如果规格与实现不一致，停下来告诉我差距，并给出三个处理选项：
(1) 改实现；(2) 改成不带数字/限定口径的叫法；(3) 补测后再写。
不要直接改文案。
```

**期望输出**：差异清单 + 三个选项 + 推荐。
**失效**：模型仍想“润色” → 要求它引用 RTL 行号/日志行。

---

## 9. 收尾

```text
收尾请给我四件事：
1) 改了什么（文件/行为）；
2) 验证了什么（命令/结果/证据路径）；
3) 还差什么（未完成/风险/边界）；
4) 已更新哪些文档/记忆/提交（commit/tag）。

如果会话可能被上下文上限硬切，先落盘再继续。
```

**期望输出**：四段式收尾 + commit/tag。
**失效**：只写“完成了” → 要求证据路径。

---

## 10. 事故复盘 / 踩坑清单

```text
把这次事故整理成一条可复用清单：
- 触发条件（什么情况下会发生）；
- 症状（怎么被发现）；
- 根因（证据）；
- 修复（最小改动）；
- 预防（门禁/脚本/提示词）；
- 失效条件（什么情况下这条不适用）。
写成结构化条目，放进 pitfalls/。
```

**期望输出**：一条可直接复用的踩坑条目。
**失效**：只写“注意一下” → 要求触发条件与排查步骤。

---

## 11. 报告 / 技能包提炼

```text
把本项目的过程整理成两份材料：
A. 设计报告：背景/创新/原理框图/软硬件划分/优化前后对比/测试/复现；
B. 技能包：每项写清适用范围、使用方法、失效条件、已验证效果、来源失败。
要求：
- 所有数字给出处（文件/日志/命令）；
- 负结果也写，并说明为什么保留/回退；
- 不夸大；每个数字有出处，不确定的标注“待复跑”。
```

**期望输出**：可提交的 Markdown + 证据索引。
**失效**：模型开始“润色”数字 → 要求逐条引用源文件。

---

## 12. 多会话/并行工作线协调

```text
现在有两条工作线：
- A：<PL 构建/上板>，占用工程目录与板子；
- B：<文档/报告>，只写 report/ 与 skill/。
请明确：
- 两边各自可以改哪些文件；
- 哪些资源互斥（Vivado 工程、VDMA、板子）；
- 交接点（构建完成后把 bit md5/时序/资源写到哪个文件）。
不要同时操作同一工程目录。
```

**期望输出**：文件/资源分工 + 交接点。
**失效**：两个会话同时开 Vivado → 工程锁冲突/互相踩。

---

## 附：一句话原则

> **让模型跑得快，让门禁说得准，让人做最终判断。**
