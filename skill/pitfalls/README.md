# pitfalls —— 结构化踩坑清单

> **类型**：踩坑清单
> **适用场景**：任何 FPGA / PYNQ 项目（不限本队题目与板卡）。按领域分六类：A 构建/时序、
> B DMA/内存、C 视频链路/显示、D 部署/运维、E 大模型协作、F 板卡现场——
> 你按自己卡住的那一类跳进去读。
> **用法**：项目开始时通读；遇到相似症状先按每条的“修复/预防”走，不要从零猜。
> **已验证的效果**：31 条全部来自本项目 2026-09 → 2026-11 真实触发过的事故，
> 每条都带可核对的指纹数字（如 `errs=0x08`、相邻帧一致性 10%、WNS −1.035 /
> 1287 个端点失效、LUT 74.5%→79.6%），「预防」一栏给出的门禁脚本已在构建/上板流程里实际使用。
> **失效条件**：逐条写在每条的“失效”一栏（如 LUT < 60% 时 A6 不适用、纯 PS 改动不受 A1 约束）；
> 本清单只覆盖本项目踩过的，不是平台全量错误表。
> **来源**：本项目 2026-09 → 2026-11 的真实事故（项目工作记录：问题清单、交接文档、
> 协作章程；这些是过程文档，未随提交包）。每条都写：触发条件、症状、根因、修复、预防、失效条件。

---

## A. 构建 / 时序

### A1. 改 RTL 后 bit 里还是旧逻辑（IPCACHE / OOC 静默复用）

- **触发**：修改了 BD 内 module_ref 的 RTL（如 `max_bounce`），只 relaunch 父级综合。
- **症状**：时序过、台架绿、bit md5 变了、能下板；但上板逐位对拍全不符。
- **根因**：BD 里的 module_ref 有独立 OOC 子运行；父级 relaunch 不会重跑子运行，
  日志只有一行 “Using cached IP synthesis design”。
- **修复**：删除 `proj/<name>.cache` 与 `.gen`，`reset_run` **所有** run，整棵树重新综合。
- **预防**：改 RTL 只允许走 `build_after_patch.tcl`；上板前跑逐位台架。
- **失效**：纯 PS 改动不需要；只改约束时视情况。

### A2. 从零重建丢 IP / 复活 ILA

- **触发**：用 Tcl 从零重建 BD，脚本漏了某两个 IP，或旧的 ILA 又被加回。
- **症状**：构建 exit=0，台架可能全绿；但某个功能（风暴/PL 检测）直接哑掉。
- **根因**：BD 脚本与 RTL 列表不同步；没有产物级对账。
- **修复**：用 `.hwh` 与 `ip_baseline.json` 逐 IP/地址对账；补回 IP 并更新脚本。
- **预防**：`finish_build.py` 每次构建后自动对账；`ip_baseline.json` 纳入版本控制。
- **失效**：工程没有基线文件 → 首次成功构建后生成。

### A3. Vivado 失败但 exit=0

- **触发**：IP definition not found、无源引脚、时钟没解出来。
- **症状**：脚本继续往下跑，最终“完成”。
- **根因**：Vivado 批量模式只打 ERROR，不返回非零。
- **修复**：在 Tcl 里加硬门禁（IP 目录查询、无源引脚、采集链、时钟求解值、时序），
  失败 `exit 1`。
- **预防**：看门禁文本，不看返回码。
- **失效**：门禁本身写错 → 定期用“故意破坏”验证门禁会响。

### A4. 大数组被推断成 LUTRAM，器件装不下

- **触发**：RTL 里的大数组（stats/par/缓存）让 Vivado 自由推断。
- **症状**：OOC 综合 LUTRAM 24,512，器件只有 17,400；整机装不下。
- **根因**：小容量多端口数组被推断成分布式 RAM。
- **修复**：强制 Block RAM + 显式单读口；必要时改流水/降端口。
- **预防**：OOC 综合后先看 `LUT as Memory`；大数组默认加 RAM 属性。
- **失效**：真正需要多端口小数组时，LUTRAM 可能更合适。

### A5. 时序门禁被绕过

- **触发**：WNS/WHS 为负仍下 bit，“先看看功能”。
- **症状**：大部分功能正常，现场偶发死机/花屏。
- **根因**：没有门禁或门禁只警告。
- **修复**：违例 bit 自动改名 `.TIMING_FAILED`，禁止下板。
- **预防**：`timing_gate.tcl` 作为构建最后一步；CI/脚本检查。
- **失效**：跨时钟域/异步路径需要额外约束，不能只看 WNS。

### A6. 资源顶到 80% 后，时序断崖式崩（布图拥塞，不是逻辑写错）

- **触发**：加逻辑让 LUT 从 74.5% 涨到 79.6%，RTL 其余部分没动。
- **症状**：同一套策略，WNS 从 +0.085 掉到 **−1.035**，**1287 个端点**失败；
  最差路径**布线占 9.03 ns，逻辑只有 1.7 ns**。
- **根因**：不是新逻辑太长，是布线资源被挤到只能绕远路。
- **修复**：**只重跑实现**（复用 synth dcp），place 换 `ExtraNetDelay_high`，
  route `NoTimingRelaxation` + post-route phys_opt `Explore` → +0.094 / 零失败端点。
- **预防**：资源过 75% 后，每次构建都先看“最差路径的布线占比”，
  布线 > 逻辑 3 倍就是布图问题，改逻辑没用。
- **失效**：LUT < 60% 时基本不会遇到；跨时钟域违例要另外约束，不适用本条。

## B. DMA / 内存

### B1. 野 DMA 覆写 CMA

- **触发**：脚本崩溃/被 SIGKILL，未执行 `atexit`；VDMA 仍在跑。
- **症状**：相邻帧一致性 10%、帧率 3 fps、`errs=0x08`、帧索引只有 1。
- **根因**：VDMA 是 PL 硬件，不随进程退出而停；它带着已释放的缓冲地址继续写。
- **修复**：`vdma_state.py --halt` 停通道；再 allocate/load。
- **预防**：起采集/下 bit 前先查 `DMACR.RS`/`DMASR.halted`；脚本保证 `atexit` 停 DMA。
- **失效**：没有 VDMA/自定义 DMA 的项目不适用。

### B2. 两个 VDMA 客户端同时跑

- **触发**：实时预览与抓帧同时开。
- **症状**：花屏、帧错乱、偶发段错误。
- **根因**：两个进程抢同一 VDMA/CMA。
- **修复**：改为互斥（文件锁/状态文件）；停一个再开另一个。
- **预防**：启动脚本检查状态文件；文档写明互斥。
- **失效**：多通道 VDMA 且缓冲独立时可并行。

### B3. 用 mtime 判断“是否最新”

- **触发**：部署/备份时比较文件时间或大小。
- **症状**：偶发漏判（NTFS 延迟更新、FAT 2 秒粒度）。
- **根因**：文件系统时间戳不可靠。
- **修复**：用内容 md5/SHA256。
- **预防**：所有“是否最新”的判据统一用 md5。
- **失效**：超大文件可采样哈希，但要有明确规则。

### B4. 在 FAT `/boot` 跑脚本/存状态

- **触发**：把脚本或状态文件放 `/boot`。
- **症状**：断电后文件丢失/截断。
- **根因**：FAT 无日志，断电易丢写。
- **修复**：全部放 ext4（如 `/home/xilinx/wp`）。
- **预防**：铁律写明“绝不在 /boot 跑或依赖 /boot”。
- **失效**：只读固件文件可放，但不要写。

### B5. 读出来的还是上一帧（缓存一致性）

- **触发**：`pynq.allocate()` 拿到的是 **cacheable** CMA 缓冲，PL 却直接写 DDR。
- **症状**：CPU 侧读到旧数据；小数据“有时对有时不对”、连读两次结果不同、
  换块缓冲就好、改成 `cacheable=False` 又变慢。
- **根因**：PL 的写不经过 CPU cache；CPU 读命中自己的 cache 行，看不到 DDR 的新值。
  反方向同理：CPU 写完没 `flush()`，PL 读到旧 DDR 内容。
- **修复**：**读前 `invalidate()`、写后 `flush()`**。封装见
  `pynq-safe-overlay/scripts/cma.py`（`PlBuffer.snapshot()` / `.fill()` 内部各做一次）。
- **预防**：凡是“PL 写、CPU 读”的缓冲，一律在返回给上层之前 invalidate；
  本队 `vdma_capture.py` 就是这么做的（注释原文“PL 直写 DDR，绕过 CPU 缓存”）。
- **失效**：用 `/dev/mem` mmap 的非缓存映射（本队 `fastmem.py`）不需要，flush 是空操作。

## C. 视频链路 / 显示

### C1. 链路“半死”（花屏 / 行长度异常）

- **触发**：视核 resync 在 aclk 域，soft_rst/ctrl[3]/传感器断电都无效。
- **症状**：行长度 1254、花屏、帧冻结。
- **根因**：视核内部状态坏了，软件复位够不到。
- **修复**：重下 bit（唯一入口 `load_bit.py`）。
- **预防**：演示前重下 bit；不要盲目改软件。
- **失效**：如果是 pclk/线材问题，重下 bit 也不治——先看 A/B。

### C2. frame_cnt 不动 ≠ 链路死

- **触发**：VDMA 停了，AXI-Stream 没有消费者。
- **症状**：帧计数不变，误判为相机坏了。
- **根因**：AXI-Stream 需要消费者；VDMA 一停流就堵住。
- **修复**：先读 `DMACR.RS` / `DMASR.halted`，再下结论。
- **预防**：把“帧计数/VDMA 状态/错误位”一起看。
- **失效**：真正的 sensor 掉电需要看 I2C/电源。

### C3. 相机链路每行多 1 字节 / 帧冻结

- **触发**：PLL 倍频器配置导致 pclk 偏高。
- **症状**：行长度异常、帧冻结；换旧 bit/冷启动都不治。
- **根因**：pclk 频率超出链路余量。
- **修复**：PLL 倍频器 `0x3036:105→52`，pclk 降到 42 MHz。
- **预防**：改相机配置后跑链路台架；保留 A/B 旧 bit。
- **失效**：线材/转接板问题需要硬件处理。

### C4. HDMI 随机水平偏移 / 卷轴

- **触发**：Master/Slave、`vtg_ce`、`gen_clken` 三件套不匹配。
- **症状**：画面随机偏移/卷轴式接缝；重下 bit 时好时坏。
- **根因**：显示时钟域边界错误。
- **修复**：按 rgb2dvi 要求重配三件套；修 `aux_reset_in`。
- **预防**：先用彩条隔离（彩条对=时序问题）；冷启动兜底。
- **失效**：如果是显示器兼容性，换屏/换时序。

### C5. MM2S DMACR 写错导致 0 帧

- **触发**：MM2S `DMACR` 写成 `0x5001`。
- **症状**：能跑但 0 帧。
- **根因**：需要写 `0x0001_1089`。
- **修复**：改为 `0x00011089`。
- **预防**：把常量写进驱动并台架断言。
- **失效**：不同 VDMA 版本位定义可能不同，以手册为准。

### C6. rgb2dvi 字节序

- **触发**：直接按 RGB 打包。
- **症状**：颜色错（红蓝/绿错位）。
- **根因**：rgb2dvi 期望 `{R,B,G}`。
- **修复**：软件层 `(R<<16)|(B<<8)|G`。
- **预防**：彩条/纯色测试。
- **失效**：不同 IP 版本可能不同，以实测为准。

### C7. 图上中文变 `?????`

- **触发**：`cv2.putText` 用 Hershey 字体写中文。
- **症状**：一排问号。
- **根因**：Hershey 不含中文字形。
- **修复**：图上只用 ASCII；中文留给控制台/网页。
- **预防**：代码审查/截图检查。
- **失效**：改用 PIL/FreeType 可写中文，但要带字体文件。

## D. 部署 / 运维

### D1. `sudo` 成功不代表口令对

- **触发**：用 `sudo` 是否成功验证口令。
- **症状**：缓存 ticket 续期，错误口令也“成功”。
- **根因**：sudo 时间戳缓存。
- **修复**：用 `sudo -k` 后再验证，或直接 `su` 测试。
- **预防**：不要用 sudo 成功做口令判据。
- **失效**：无。

### D2. 命令管道结尾的 rc 是假的

- **触发**：`cmd | tail`。
- **症状**：`$?` 是 tail 的返回码。
- **根因**：管道最后一段的退出码。
- **修复**：`; echo rc=$?` 或写日志再查。
- **预防**：脚本里用 `set -o pipefail` 或分开执行。
- **失效**：无。

### D3. 部署清单手写过期

- **触发**：新增脚本没加进 deploy 清单。
- **症状**：板上缺文件，但构建“成功”。
- **根因**：清单与目录不同步。
- **修复**：扫目录生成清单；`deploy_check.py --fix`。
- **预防**：提交前跑 `deploy_check.py` + md5。
- **失效**：动态生成的文件需单独规则。

### D4. `pkill -f "xxx.py"` 杀掉自己

- **触发**：SSH 命令行里含 `xxx.py`。
- **症状**：命令把自己杀掉；脚本目录被重置。
- **根因**：`pkill -f` 匹配整条命令行，包括自己的 shell。
- **修复**：用 PID 杀；或 `[x]xx.py` 技巧。
- **预防**：杀进程用 PID；构建命令显式 `cd`。
- **失效**：无。

### D5. 启动服务与 SSH 命令互相匹配

- **触发**：`systemctl start magnetic-demo` 与含 `ball_game.py` 字样的命令写在同一行 SSH。
- **症状**：服务“让位”退出。
- **根因**：`start_demo.sh` 的 `pgrep -f "[b]all_game.py"` 匹配到这条 shell。
- **修复**：分两条 SSH；或改 pgrep 模式。
- **预防**：启动脚本用更精确的匹配（PID 文件）。
- **失效**：无。

### D6. 部署目录里躺着旧 md5 边车，校验“通过”但下的是旧 bit

- **触发**：每次构建生成 `<name>.bit` + `<name>.bit.md5`；历史版本改名后
  留下 `<name>_949911fb.bit.md5` 之类的旧边车（本项目 deploy 里**曾经**同时有两个：
  当前 `ov5640_m1a_wrapper.bit.md5` + 10-28 的 `ov5640_m1a_wrapper_949911fb.bit.md5`，
  后者已按本条移出部署包）。
- **症状**：最坏的情况是**校验通过、下进去的是旧逻辑**（新边车配了旧 bit）；
  次坏是 `load_bit.py` 报“md5 不一致”，一群人以为是构建坏了。
- **根因**：边车文件与 bit 不是原子的一对；靠文件名关联，不靠内容。
- **修复**：出 bit 后跑三方对账 —— **impl_1 产物 == 部署副本 == 边车里记的**
  （`vivado-repro-gate/scripts/bit_freshness.py`）；旧边车要么删，要么挪出 deploy
  （本项目选了移出部署包，部署包里只留当前 bit 的那一个）。
- **预防**：`finish_build.py` 里把“边车与产物同源”做成硬门禁；
  部署包里**只允许存在当前 bit 的那一个 `.md5`**。
- **失效**：不用边车、每次现场 `md5sum` 现算的流程不受影响（慢一点，但不会错）。

## E. 大模型协作

### E1. 模型说“改了”，但没有证据

- **触发**：模型说“已修改/已通过”，但没有 diff/日志。
- **症状**：文件没变、构建没跑、台架没过。
- **根因**：生成式模型的“完成”是语言行为，需要独立核对。
- **修复**：要求 diff/命令/原始输出；用 `git status` 核对。
- **预防**：每步给证据路径；关键改动人工复核。
- **失效**：无。

### E2. 规格与实现不一致

- **触发**：对外叫法、并行度、性能数字与 RTL 参数/实测不一致。
- **症状**：答辩或评审时被问住，或者复现结果对不上。
- **根因**：先改文案，没有同步实现或测试。
- **修复**：改实现 / 改口径 / 补测，三选一。
- **预防**：规格审计提示词；提交前做口径核对。
- **失效**：无。

### E3. 上下文 1M 硬切

- **触发**：单会话过长。
- **症状**：API 400，无法继续。
- **根因**：模型上下文上限。
- **修复**：新会话“查对话 N”接手；状态从 HANDOFF/记忆恢复。
- **预防**：每完成一块就提交+落盘；长任务分段。
- **失效**：无。

### E4. 注释/文档与译码不一致

- **触发**：驱动按过期注释写寄存器地址。
- **症状**：轮询到错误状态（如把 n_alive 当 STATUS），误判 busy。
- **根因**：注释过期，代码以译码为准。
- **修复**：以 RTL 译码/实测为准；更新注释。
- **预防**：寄存器映射单一来源；台架断言。
- **失效**：无。

## F. 板卡现场

### F1. 救援阶梯不限频 → 自造死循环

- **触发**：反复断电/重上电/重配。
- **症状**：初始化每次被打断，越救越坏。
- **根因**：救援动作之间没有静默窗口。
- **修复**：≥5 s/次；升级动作后静默 ≥10 s；连续失败放弃。
- **预防**：把频率写进现场脚本/文档。
- **失效**：无。

### F2. 跳线帽导致不亮/不启动

- **触发**：电源/启动跳线帽缺失或错位。
- **症状**：开机不亮/不启动。
- **根因**：PYNQ-Z2 需要电源（REGUSB→REG）与启动（SD）两帽；PLL/JTAG 默认无帽。
- **修复**：按板卡说明装回。
- **预防**：现场清单先查帽。
- **失效**：不同板卡跳线定义不同。

### F3. 盲目下 bit 导致总线挂死

- **触发**：PL 处于半编程/未知状态时直接下 bit。
- **症状**：PCFG_INIT 超时、MMIO 挂死、只能断电。
- **根因**：PL 配置状态不确定。
- **修复**：断电重启；之后只用 gated 脚本。
- **预防**：下 bit 前 `pl_probe`；rc=9 不下。
- **失效**：无。

## 附：怎么新增一条

新增踩坑条目时，至少写清：

1. **触发条件**（什么情况下会发生）；
2. **症状**（怎么被发现，最好有指纹数字）；
3. **根因**（证据，不是猜测）；
4. **修复**（最小改动）；
5. **预防**（门禁/脚本/提示词）；
6. **失效条件**（什么情况下这条不适用）。

没有“触发条件”和“排查步骤”的条目，对别人没有用。
