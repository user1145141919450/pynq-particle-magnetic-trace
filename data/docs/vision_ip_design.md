# PL 视觉前处理 IP 设计规划（V1）

> 2026-09-23 晚。工具链：Vivado 2023.2 / PYNQ-Z2（XC7Z020）。
> 本文是"原理图"，过一遍再动 RTL（沿用用户定的"先原理图后改代码"）。

---

## 1. 要解决的问题（用今晚量出来的数说话）

| 在哪算 | 逐帧耗时 | 折算帧率 |
|---|---|---|
| PYNQ 的 PS（ARM Cortex-A9） | 423 ms（背景差分）/ 743 ms（霍夫圆） | 1.3~2.4 fps |
| 同一算法在 PC 上 | 16~28 ms | 35~60 fps |
| 游戏需要 | ≤ 33 ms | 30 fps |

而且更糟：PS 一算检测就抢 DDR 带宽，**连采集都从 17fps 掉到 5fps**（实测 抓帧 187ms vs 57ms）。

一句话：**147 万字节/帧 × 30 帧/秒 的图像数据从 PL 搬进 PS 内存，再由 CPU 逐像素处理 —— 这条路走不通。**

## 2. 设计取舍：PL 做什么、不做什么

### 结论：PL 只做"8×8 块平均降采样"，**分类/识别全部留在 PS**

降采样后 PS 拿到的是 **128×90 的 RGB565 缩略图（23KB/帧）**，数据量降到 **1.6%**。

**为什么不把颜色分类、连通域也搬进 PL？**

1. **判据会变**。红/蓝/黑球的阈值随光照、桌面、球的材质变；今晚就因为"灰度差太钝""黑球在暗底上看不见"反复调过阈值。判别逻辑写在 RTL 里 = 每改一次阈值就要重新综合、重新下板（15 分钟起），写在 Python 里 = 改一行、下一条命令。
2. **游戏要认的不止是球**。玩法里还有"玩家自己摆的黑球洞口""实体障碍""传送门"—— 这些也会出现在画面里。降采样是**通用**的：以后要认什么新东西，PS 端加代码即可，PL 不用动。
3. **可以严格证明对不对**。块平均是线性的，黄金模型就是一行 `cv2.resize(img, (128,90), interpolation=cv2.INTER_AREA)`，逐字节可对。
4. **风险最小**。这套采集链今晚刚修好（VSIZE 722→720），绝不能再动它。本 IP 是**纯观察者**：只接 s_axis 的信号当输入，**不产生 tready、不改数据**，对现有链路零影响。

**代价**：8×8 平均会把细窄的东西（线材、阴影边、5px 的电缆）抹掉。对玩法反而是好事（**天然的杂物抑制**）；球直径 20~40px，在缩略图上仍是 2.5~5 块的实心斑，位置精度 ±4px（≈±2.4mm），够用。

## 3. 数据流

```
        ┌─────────────── PL（100MHz aclk） ───────────────┐
        │                                                  │
OV5640 ─┤ ov5640_top ─ dvp2axis_bridge ─┬─→ axis_probe ─→ VDMA(S2MM) ─→ DDR ─→ PS
 (DVP)  │   (pclk 域)   10bit→16bit      │      (现有链路，一行不动)
        │                                │
        │                                └─→ vision_core ★新增（纯观察，不产生 tready）
        │                                        │
        │                                        │ 8×8 块平均（RGB565，64 像素求和>>6）
        │                                        ↓
        │                                   map_ram 128×90×16bit = 23,040 B（32KB BRAM）
        │                                        ↑ 读口 B
        └──────────────────────── axi_bram_ctrl ─┘
                                     ↑ AXI4-Lite
                                     └──────── PS：mmap(/dev/mem) + numpy 一次读 23KB ≈ 1 ms
```

PS 侧每帧拿到缩略图后做的事（都在 128×90 上，代价 ≈ 1/64）：
```
缩略图 ─┬─ 颜色掩膜（红/蓝/黑，阈值可调）
        ├─ 背景差分（PS 自己在内存里留一张"空桌缩略图"，不占 PL 资源）
        ├─ 形态学 + 连通域 → 球的质心/半径
        └─ 相机坐标 → 场区坐标（单应矩阵，标定一次）
```

## 4. RTL 细节（vision_core.v，预计 ~150 行）

### 4.1 块累加
- 输入：s_axis 的 `tdata[15:0]`（RGB565）、`tvalid`、`tready`、`tuser`（帧首）、`tlast`（行尾）
- **只统计被对方接受的拍**（`tvalid && tready`），保证与 VDMA 看到的一致
- 拆通道：`R=(v>>11)&0x1F`、`G=(v>>5)&0x3F`、`B=v&0x1F`
- 列累加器：128 列 ×（R 12bit + G 12bit + B 12bit）= 36 bit/列
  → 用 **1 个真双口 BRAM36**（128×36）做读-改-写，每像素 3 拍（读、加、写），而 aclk 有 4.5 拍/像素（100MHz / 22.2M 像素/秒）→ 有富余
- 行计数：每 8 行（`tlast` 计 8 次）把 128 个列累加器 >>6 写成一行块平均，写进 map_ram，然后清零列累加器
- 每帧 90 行块 → 90×128 = 11,520 个块
- `tuser` 复位行计数与列累加器（防帧错位后累积污染）

### 4.2 字节序无关（重要且省事）
RTL 不关心高低字节谁在前：翻转字节序只是把 R/B 两个**线性**通道对调，块平均跟着对调。
→ **PS 侧读回缩略图后，用现有的"通道相关性自动判定"决定要不要交换**，PL 一个字都不用改。

### 4.3 时序与验证钩子
- `frame_cnt`：每帧 +1，PS 用它判断"这一帧的缩略图是否已就绪"（读前读后各读一次，不等就重读）
- 一个 `latch` 位：置 1 后停止更新 map_ram（冻结一帧），PS 读到的就是**同一帧**的快照 → 与同一次全分辨率抓帧做黄金模型对比（静态桌面即可）

## 5. 地址与寄存器规划

| 地址 | 内容 | 说明 |
|---|---|---|
| 0x4300_0000 | axi_vdma（现有） | 不动 |
| 0x43A0_0000 ~ 0x43A6_0000 | 各 axi_gpio_probe（现有） | 不动 |
| **0x43B0_0000** | **axi_bram_ctrl → map_ram（32KB 窗口，用其中 23,040 B）** | PS 用 mmap 读 |
| **0x43B1_0000** | **axi_gpio_vision（ctrl/status）** | 见下 |

寄存器（axi_gpio，2 路输出 + 1 路输入）：

| 位 | 名称 | 作用 |
|---|---|---|
| out0[0] | enable | 1 = 累加并更新 map_ram；0 = 冻结 |
| out0[1] | soft_rst | 清列累加器/行计数（在线复位，不重下 bit） |
| out0[2] | latch | 冻结当前帧的快照（验证用） |
| out1[31:0] | （备用） | 后续 V2 的阈值/统计用 |
| in0[31:0] | frame_cnt | 已完成帧计数（PS 判"缩略图已刷新"） |
| in0 高 16 位 | （备用） | 可放"本帧块数/越界计数" |

## 6. 资源预算（XC7Z020：140 BRAM36 / 220 DSP / 53K LUT / 106K FF）

| 资源 | 本 IP 用量 | 占比 |
|---|---|---|
| BRAM36 | 8（map_ram 32KB）+ 1（列累加器）+ 1（axi_bram_ctrl 内部，可能 0） | ≈ 7% |
| LUT | ≈ 700（累加器控制 + 通道拆分 + 行/列计数 + 状态） | ≈ 1.3% |
| FF | ≈ 600 | < 1% |
| DSP | **0** | 0% |

**结论：代价极小，剩余资源完全够后面的"并行轨迹束扫描"和 HDMI 输出。** 这也是选"只做降采样"的另一个理由——把预算留给真正的创新点。

## 7. 验证计划（分四步，每步都有判据）

1. **黄金模型（PC）**：`cv2.resize(原始帧, (128,90), INTER_AREA)` → 期望缩略图。写进 `software/pc/vision_golden.py`。
2. **板端一致性**：下新 bit → 冻结 map → mmap 读回 → 与黄金模型逐字节比。**判据：≥98% 字节完全相同，差异 ≤1 LSB**（取整方向差异）。这一条过了，PL 就算验收通过。
3. **端到端**：PS 在缩略图上跑检测（颜色掩膜 + 背景差分 + 连通域），与现有全分辨率检测器的球坐标对比。**判据：红/蓝/黑球数量一致，坐标偏差 ≤ 8px（=1 个块）。**
4. **性能**：量三条时间线 —— 采集 30fps 不变、缩略图读回 ≤2ms、PS 检测 ≤5ms。**判据：端到端 ≤ 33ms（30fps 全速）。**

### 7b. v2 实现修正（2026-09-24，上板实测后回头改的）

上面第 4 节是**动手前的规划**，上板实测后有三处必须改。留着原文是因为"计划怎么错的、
实测怎么纠正的"本身就是比赛材料里最有说服力的部分。

| # | 规划里的写法 | 实测后改成 | 为什么 |
|---|---|---|---|
| 1 | 列累加器用 **1 个真双口 BRAM 做读-改-写**（每像素 3 拍） | **寄存器数组** `sum[128][34bit]`（4352 FF = 106K 的 4%） | 行内字节是**背靠背**来的（2 拍/像素），3 拍/像素的 RMW 在行内跟不上；而且那个 BRAM 的两个口，一个要给 PS、一个要给累加器，本来就不够 |
| 2 | "字节序翻转只是 R/B 对调，PS 侧处理即可" | **RTL 加 `swap_bytes` 控制位，先对调再拆通道** | 字节序不同时 16 位值的**位域含义整体重排**（不是 R↔B）。直接累加原始 16 位再"事后解释"是错的，必须先拆 R/G/B |
| 3 | "8 行凑满 → 进 flushing 状态刷 64 拍"，并假设它落在行消隐里 | **刷写折叠进第 8 行**：某列的最后那个像素一走完，该列 64 像素就凑齐了，当拍取平均写走（偶列暂存、奇列拼字） | ★ **假设被实测推翻**：`flush_ovl` sticky 位点亮 → 刷写期间真有字节到来 → 那些字节被丢 → 像素字节配对整体错位一位 → 缩略图与黄金模型相关性 **0.05**（有内容、有彩色、行数也对，但**数值全错**）。v2 的刷写散落在整行里，不占任何额外时间窗口，从机制上没有可丢字节的地方 |

另外补了一条规划里没想到的：**resync**（复位只在帧边界生效）。上电 / `soft_rst` /
撤销冻结后，模块丢弃输入直到下一个帧首（`tuser`）才开工。否则复位落在行中间时，
字节相位会被锚在随便一个奇偶位上，那一行必然错位、还会点亮错误位 —— 看起来像
"设计有 bug"，其实是"复位时机没法保证"。等帧首开工，代价最多一帧（36ms）。

### 7c. 上板验收时抓出来的另外两个 bug（2026-09-24 深夜）

**#4 列写使能漏了"末像素"这个门 → 8 倍写入。** v2 第一版把列写入放在
`row_in_blk == ROW_LAST` 上，但**没检查"这是本列的最后一个像素"**，于是奇数列的
每个像素都触发一次写入：一帧 8×5760 = 46080 次，15 位的 `wcnt` 溢出，
`46080 − 32768 = 13312 = 0x3400` —— 板上读回的 `last_wcnt` **正是这个数**，
`errs` 只亮 bit2（写字数超过 5760），两者互为印证。

★ **这个 bug 的可怕之处在于缩略图内容还是对的**：同一地址被反复覆盖，最后一次覆盖
正好是列和。所以"看图有内容、有彩色、行数也对"一条都拦不住它 —— 是自检字
（`stat`/`errs`）把它抓出来的。**"结果碰巧对"绝不能当验收判据**，这条在这又应验一次。

**#5 桥的丢行机制会吃掉帧首（SOF），形成自锁死锁 —— 而且它不是新 bug，是被这次改动
"叫醒"的既有设计缺陷。**

VDMA 配的是 `FSYNCSEL=2`（tuser 帧同步）：**没有 tuser 就不启动一帧，不启动帧就不取数**。
桥的丢行判据是"行起点水位 > 4096 就丢整行"，而丢行连 `eol`/`sof` 一起丢：

```
水位 >4096 → 吞整行（含驮 SOF 的那行）→ 没有 push → sof_armed 落不下来
          → 本场不发 SOF → VDMA 不取数、水位降不下去 → 下一场继续吞行 → 自锁
```

**怎么证明的（这一步是这次排障里最值钱的）**：让 PS **完全不动**（只睡 12 秒，
不抓帧、不打印、不 memcpy），变量只剩 PL 自己 —— 仍然是 `push/href = 0.125`、
每场只有 **90/720 行**、`tuser 3.75/s`。而 12 秒内 VDMA **恰好完成 45 帧 = 45 个
tuser —— 一 SOF 一帧**，帧率被 SOF 率锁死。**这个对照实验把"PS 抢 DDR 带宽"这个
本工程的老嫌疑人一次排除干净。**

修法一行，且余量可算不算猜：

```verilog
dropping <= (wr_data_count > 14'd4096) & ~sof_armed;   // 带 SOF 的行绝不丢
```

`sof_armed` 从 vsync 上升沿武装、到第一次 push 才落下 —— 它=1 的那一刻，走的正是
"本场还没送出帧首"的行。放行一行最多 2048 字，而阈值 4096 到深度 8192 之间正好留了
4096 字，**放这一行永远越不过满水位**（这个余量本来就是当初选 4096 当阈值的原因）。

**#6 帧首落在行中间 → 像素网格每帧随机偏半个像素（第十五版修复）—— 这是 C 项 0.2% 的真因**

C) 项（板端 map 与黄金模型逐块比）一直 ~0.2%，两张图拉出来看**都是彩色噪点**。
定位方法（可复用）：把抓回的整帧按"行内字节偏移 0..3"各配一次像素，算平均 |水平梯度|
—— 真画面相邻像素强相关（梯度小），配错字节就是噪点（梯度大）：

```
偏移 0：7332（噪点）      偏移 1：648（真画面）
```

→ **整帧网格偏了整整一个字节 = 半个像素**（正是 RTL 里 `errs` bit0 那个名字
"tlast 落在半个像素上"的由来）。再连抓 4 帧逐帧量偏移：

```
修复前：偏移 = [1, 2, 0]      ← 帧间连奇偶都在变
修复后：偏移 = [3, 1, 1, 3]   ← 全奇数（1 与 3 差 2 字节 = 正好一像素，同一相位）
```

**根因**：`sof_armed` 由 vsync 上升沿武装、**由"下一个 push"消费**，而
`push = href_d & ~dropping & ~wr_rst_busy` 会被挡；一挡，帧首就落到**某一行中间**。
（同时也解释了 `errs` bit0 为何时有时无 —— 取决于落点的奇偶。）

**为什么它让 C) 永远对不上**：板端 map 与黄金模型**都从帧首那个字节开始配对**。
帧首位置每帧随机 → 抓 raw（T1）与读 map（T2）落在不同网格上 → 逐块对比必然 ~0.2%。
**它不是"数值算错"，是"两张图根本不在同一个像素网格上"。** 对游戏同样致命：
相位随机的帧，等于每帧都在错位的图上算球的位置。

**修法**：帧首只在**行首**转正（`sof_pending` 记账 → `line_start` 转正 → 该行被丢则继续欠着）：

```verilog
if (vsync_rise) sof_pending <= 1'b1;                        // 武装（只记账）
if (line_start)
    if (sof_pending) begin sof_armed <= ~dropping; sof_pending <= dropping; end
else if (push)      sof_armed <= 1'b0;                       // 该行第一个字节用掉 SOF
```

**#7 丢行判据必须是"这一行放不放得下"，且 SOF 行要单独放宽（普通 4096 / SOF 6144）**

两条要求互相拉扯，前面两版各错一半（都上板实测过）：

- **要求① 永不溢出**：溢出丢的是**字**（FIFO 10 位宽，一次丢一个 `{sof,eol,data}`）→
  行内字节数变奇数 → 之后所有像素**配对整体错一位**。实测：`errs` bit0 + map 只有前
  1/4 有内容 + C 项 0.2%。**第一版"无条件强行放行 SOF 行"违反了这条。**
- **要求② 帧首必须送得到**：VDMA 是 tuser 同步 —— 没 tuser 就不启动帧、**不启动帧就不取数**。
  帧间空隙里桥还在推（44M 字/秒），水位必然爬到 4096 以上；若 SOF 行也按 4096 丢，就再也
  没有帧首 → 死锁。实测：每场只剩 **90/720 行**、`tuser 3.75/s`、12 秒内 VDMA 恰好 45 帧
  = 45 个 tuser（**一 SOF 一帧**，帧率被 SOF 率锁死）。**第二版把阈值整体抬到 6144 违反了
  这条**（普通行也让位 → 水位更易越过 6144 → 连 SOF 行一起丢 → 又锁死，每场只剩 2.1 行）。

同时满足的唯一取法 —— **两种行各留一整行（2048）的余量**，于是"放行就绝不溢出"是恒等式：

```verilog
dropping <= (wr_data_count > (sof_armed ? 14'd6144 : 14'd4096));
//  ≤4096 起推，整行推完最多到 6144 ≤ 8192 ✓
//  ≤6144 起推，整行推完最多到 8192 = 8192 ✓（刚好满，不溢出）
```

**这一条也别忘：VDMA 只在写帧时取数。** 所以"PS 一忙（连抓 1.5MB 整帧、BGR 转换）就抢掉
VDMA 的 DDR 带宽 → FIFO 灌满 → 丢行"是真实机制，也正是 vision_core 存在的理由本身
（让 PS 只搬 23KB）。**独立验证它的办法**：`stream_ledger.py --quiet`（PS 只睡 10s、
不碰 DDR）—— 那个窗口里若每场回到 720 行，就说明流本来是好的，别赖桥。

**#8 ★★ 真正的病根：BRAM 是"字节地址"，视核送的是"字地址"（C 项 0.1% + 只写 1/4 的元凶）**

板上生成的 IP 参数（`proj/.../blk_mem_gen_vision_0/synth/*.vhd` 的
`CORE_GENERATION_INFO`）里明写着：

```
C_ENABLE_32BIT_ADDRESS = 1      ← 就是这个
C_USE_BYTE_WEB = 1, C_WEB_WIDTH = 4
C_ADDRA_WIDTH = 32, C_ADDRB_WIDTH = 32
```

这是 **"32 位字节地址"模式**（给字节寻址总线直连用的）：送进去的地址会被当作
**字节偏移**，IP 内部再右移 2 才得到字地址。

于是 `wr_addr = {blk_row, col[6:1]}`（字地址 0..5759）被当成字节偏移 →
实际字地址 `wr_addr >> 2` = **0..1439 = 5760/4 = 整整 1/4**，而且**连续 4 次写落在同一个
字上互相覆盖** → 缩略图内容全乱、与黄金模型 0.1%。

**这就是 v1 病历里那句"写地址只覆盖前 1440 个字……1440 = 5760/4，一个 4 倍压缩"** ——
当时把它归到"字节丢了相位错位"那条线上搁下了，直到 2026-09-25 凌晨才落网。

**怎么抓到的**：填图案 → **不冻结** → 让流自己跑 1 秒 → 读回看谁被覆盖
（`src/software/board/bram_write_map2.py`）：

```
被覆盖字址 0 .. 1439（共 1440）     幸存字址 1440..5759，连续段：是
块行 20~29 覆盖 160 字 = 块行 20、21 满 + 块行 22 的一半（= 22.5 块行）
```

**1440 = 5760/4 的精确 4 倍压缩 ⇒ 地址少了 2 位。**
★ 注意我中途的推理岔路：我一度用"1440 不是 2 的幂"**排除**了地址被掩码截断 ——
这个排除本身是错的（字节地址模式下不是掩码而是右移 2，边界自然落在 5760/4）。

**修法**：`wr_addr <= {blk_row, col[6:1], 2'b00};`（×4 = 字节地址），
并把 `AW` 由 13 改成 **15**（5760 字 × 4 B = 23040 B → 15 位）。**两位宽必须同时改。**

**PS 侧本来就是对的**（`axi_bram_ctrl` 送的就是字节地址），所以 `maprw_test`
整图 11520 字读写全对 —— **这也正说明：一个自洽的字节寻址系统内部测不出这个 bug，
必须量"视核究竟写了哪些字"。**

**#9 桥的 FIFO 会在"消费者缺席"时进入丢唤醒死锁（第十五版加看门狗）**

链：VDMA 是 tuser 同步（没帧首不启动帧、不启动帧不取数）→ 消费者一停，FIFO 灌满 →
`dropping` 挡住所有行（SOF 行也挡，因为放不下）→ 帧首送不出去 → 水位永不下降 ⇒ 自锁。
**调阈值只能推迟它**（分裂阈值实测只从 2 帧推迟到 2~3 帧）。解法是**水位看门狗**：
水位持续 >6144 超过 ~5ms 就自动复位 FIFO 8 拍（`rst_pclk | wdt_pulse`），
帧首立刻送得出去 ⇒ 自愈，不需要 PS 参与。触发过就置粘滞位（7 号影子 bit31）。

### 7d. 排障方法本身踩的两个坑（记下来免得重犯）

1. **DMASR 不是 `0x14`**。AXI VDMA 的 S2MM 寄存器在 **`0x30`/`0x34`**
   （`vdma_capture.py` 的常量照 `rfs.vhd` 核过）。把 `0x14` 当状态寄存器，读出
   `0x00f74000` 还当成"帧计数停在 247"，白追一轮。**寄存器地址要么抄驱动常量，
   要么去核 IP 源码，绝不靠回忆。**
2. **账本必须在"有消费者"的时候测**。`bridge_account.py` 清零账本后干等 4 秒，
   那 4 秒 VDMA 是停的（驱动一退出就 `stop()`）。没消费者，桥的 FIFO 约 **0.18 ms**
   就灌满（8192 拍 ÷ 44.5M 拍/秒），此后每次推入都溢出 —— 于是它报出
   `c_ovf = c_push = 44.5M/s、c_rd = 0`，看起来像桥坏了。**起上 VDMA 再测：
   `c_ovf = 0`、`c_rd/c_push = 1.000`，桥本来就是好的。** 要测连接器，就得连着
   消费者一起测。

新增诊断工具：`stream_ledger.py`（账本 + 真 DMASR + 真在抓帧，三者同时测；
`--quiet` 是"PS 只睡"的对照实验）。桥的 **7 号影子槽**（原恒 0 占位）现在打包
FIFO 内部实时状态 `{dropping, sof_armed, rd_rst_busy, empty, wr_rst_busy, full,
wr_data_count}` —— 0~6 号全是事件计数、看不出**水位**，而死锁恰恰是水位解释的。

**自检设计**：v1 的教训是"看内容有没有"根本不够（v1 也有内容）。v2 把整条链路
压成两个 32 位状态字，健康值是**两个常数**：

| 地址 | 内容 | 健康值 |
|---|---|---|
| 0x43B2_0000 | `{上一帧行数, 上一帧写字数}` | **0x02D01680**（720 行 / 5760 字） |
| 0x43B2_0008 | `{行尾bcnt, errs[5:0], 本帧字数}` | **0xFFE01680**（2047 / 无错 / 5760） |

`errs` 是 **sticky**（只由 `soft_rst` 清），一个毛刺都不放过。板端一次验收跑
`vision_diag.py`，它同时验四件事：**A 结构数 / B 错误位 / C 与黄金模型逐块比 /
D 帧率**，缺一条都不算过（判据见第 7 节）。

## 9. 待拍板的两点

1. **缩略图分辨率**：8×8（128×90，23KB，精度 ±4px）还是 16×16（64×45，5.8KB，精度 ±8px）？
   **建议 8×8**：23KB 读回只要 1ms，精度也更稳。16×16 省的那点带宽不是瓶颈。
2. **颜色通道格式**：缩略图存 RGB565（每像素 2 字节，23KB）还是 RGB444（12bit 打包，17.3KB）？
   **建议 RGB565**：与传感器原生一致，黄金模型可逐位对，且 23KB 已经在预算内。
